# BioCheck · 证据约束生成与核验

维护人：潘倩。项目主目录为 zktest 的 `/home/zk_test/zk_projects/BioCheck`，主线为 `main`。

负责最终生成质量：接收已有证据、事实和研究结果，进行约束生成、细粒度核验和局部修订，可用于问答、雷达调查稿、告警理由和判断更新说明。先读 [项目说明](docs/项目说明.html)（下载后用浏览器打开）：方法、十二项任务、实验安排、接口归属和验收集中在这一个页面。

## 当前状态

本次建立的是独立维护工程和项目说明。`app/`、`tests/` 以及 `examples/good.json`、`bad.json` 来自所提供的 `drug_qa_reference_prototype.zip`，原样保留为规则教学起点。未实现完整语义核验、课题生成算法或HTTP接入；没有启动服务或调用付费模型。

原型使用虚构材料。其 `PASS` 只表示限定规则通过，不能作为医学事实正确或发布许可。当前主要限制包括：直接相信上游结构字段，没有回读原文；一句中任一数值匹配可能漏掉其他错数；数字格式覆盖有限；现有测试不能证明六类错误分别检出。

原型只完成有限规则与模板演示，不是 RefChecker、MedScore 等论文作者实现。复用论文方法时须注明出处与实际改动。

## 运行原型

需要 Python 3.10 或以上，当前原型没有第三方依赖、API密钥或网络要求。

```bash
cd /home/zk_test/zk_projects/BioCheck
python3 -m app.cli examples/good.json
python3 -m app.cli examples/bad.json
python3 -m unittest discover -s tests -v
```

模板生成示例可使用 `python3 -m app.cli examples/good.json --generate`。运行输出属于教学结果，不是论文实验成绩。后续命令只有在实现并验证后才能加入这里。

## LLM怎样接入

目标执行顺序：李的程序准备固定输入 → 潘的方法准备表达要求 → 李在预算内调用LLM得到内部草稿 → 潘核验 → 必要时李执行修订、潘复查 → 调用程序按真实状态交付。李负责是指程序自动执行，不要求逐篇由李本人操作。

潘维护内容安排、约束、核验规则与模型、回执解析和修订策略。需要生成式LLM时由李维护的统一入口实际调用并记录预算；规则和潘的轻量核验模型可直接运行并记录资源耗时。模型本地或远程，不改变这一边界。离线实验先复用获准客户端与统一实验入口，不另造模型平台。

`compose/check/revise` 是完整能力的目标入口，尚不是已接通服务。准备好的提示或约束不能冒充 `answer.compose` 的成稿；李的适配层组织请求准备、实际模型调用和结果解析后，才返回原契约要求的结果。同进程可复用已有调用函数；跨Go/Python的HTTP只能传阶段数据与模型回执，不能传Python回调。初期不自建数据库、队列、模型网关或用户前端。

规划、生成、拆分、语义核验、修订、复查及重试中的实际模型请求都计入总预算。预算不足、截断、解析失败或未完成检查不能变成PASS。研报先缓冲草稿，核验后按实际范围交付；随后实质改写的摘要、翻译或变化说明要检查新版本，不能继承旧稿通过状态。未接入前仍如实标明当前缺口。
