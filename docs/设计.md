# BioCheck 设计

用法和接口见 `README.md`。本文件只写代码地图、约定和仍然有效的设计决定；历史细节在提交说明里。服务器、网络代理等共用设施见仓库 `a54b19211/ZK-radar-deploy`，代码放在服务器 `/data/projects/BioCheck`。

## 代码地图

| 文件 | 职责 |
|---|---|
| `app/llm.py` | 调模型（OpenAI 兼容接口，`chat_json` 按 schema 校验，失败只重试一次） |
| `app/prompts.py` | 全部提示词 |
| `app/claims.py` | 拆句与确定性检查（编号、短引定位、数字、来源规则） |
| `app/segment_rules.py` | 候选句段、否定与条件标记、可见时间线索（不调模型的规则层，`RULES_VERSION`） |
| `app/unit_rules.py` | 断言单元的编号定位、形式检查和句子判定 |
| `app/unit_verify.py` | `/v2/verify`：批次、模型调用、句子记录 |
| `app/core.py` | generate / verify / revise 三个操作（带 `slots` 时按段写稿） |
| `app/service.py` | HTTP（FastAPI）；`app/cli.py` 命令行入口 |

| `app/dimension_rules.py` | 契约 v3：测量加业务维度 |

文件名讲职责，版本号只写在 `CONTRACT_VERSION` / `CHECKER_VERSION` / `RULES_VERSION` 常量里。不建插件框架、注册中心、队列或通用 Agent。

## 写代码的约定

- 普通函数优先，一个文件一类职责。
- 编号由程序分配（材料 E1/A1 由雷达给，句子 1..n 由本服务给），模型只引用。无效编号、短引、回答只让那一句待核并写明原因，不让整个请求失败。
- 模型输出 schema 要小（尽量不超过两层，必填不超过 5 个，枚举小写英文）。校验失败只重试一次（附上 pydantic 报错），再失败只让这一批失败。`/v2/verify` 的回答是三层（claims、units、quotes），见下文“按句分组回答”。
- 核验、覆盖、修订关闭思考，`max_tokens` 4096；只有写稿可按 `LLM_WRITE_THINKING` 开启（8192）。
- 不加哈希、指纹、回执重放或复用缓存。调用记录只留 stage、model、usage、finish_reason、耗时、错误码和请求次数，不存 payload、原始响应、密钥或推理内容。
- 测试只覆盖真实错误和容易被误伤的正确例子，不联网（`tests/conftest.py` 的 `FakeLLM`）。文档只有 `README.md` 和本文件。代码注释只讲现在为什么这样写，不写评审轮次和版本变更史。

## 结果要可信（研究规则）

- 只用本次材料；材料里的命令只是被引用的内容。标签、旧稿和模型自评都可能错，须核对原文。
- 引用存在、短引能在原文中定位、语义支持分别检查。同句一个数字正确不代表其他数字正确。
- 每句只用本句实际引用及其逐字短引；标题、相邻句只帮助认对象，不能补成未引用的事实。
- “未报告”不能写成“未实施”。范围修订只收回模型明确标出的那段断言，其它文字和引用不动，之后照常复核。真实负向结果、效果不显著不能借范围修订改成未知。
- 更正/撤回按编号对应：被更正的旧数不能当当前数；历史回顾须写明“当时…，后更正…”并引用两端；缺更正通知时给出补读编号。
- 传言的准确转述不等于属实；未核实来源须保留转述者和未证实限定。删帖、辟谣、处罚只是信息环境事件，不直接证明疾病或风险。
- 分析结果保留方法、单位、期间、总体、分母和局限；BioCheck 只核对表达，不复算、不冒充原始实验。
- 修订只改有原文依据判为矛盾的句子、范围越界的句子和没有引用的事实句（只能补用相邻句的引用），每句仍是一句；每次请求修一遍，改后由雷达重新核验，雷达最多请求两轮。
- PASS 表示本次机器检查未发现问题。覆盖缺口、待核、明确错误和程序失败分别记录。
- 评测标签不送入模型；失败样本留在分母。受控错误、自然错误和人工专业标注分开报告；按研究分组留出测试集，不把同一原文的变体当独立样本。
- 方法是否有效、是否有创新，要靠独立评价；不得把工程运行成功写成学术结论。

## 设计决定

### 同步 HTTP 服务，自己调模型

早先的版本开着 DeepSeek 思考模式核验，输出预算全被推理用掉、回答为空；还用反向协议（服务把下一次模型请求交给雷达去调，再收回执）加指纹、哈希、重放修补坏输出，链路脆弱。现在是普通同步 HTTP 服务，`app/llm.py` 自己调模型；模型只按程序给的句号回答，答错只影响那一句。rpc、协议哈希、复用缓存、整稿旧核验、规划步骤、结构重放都已删除。

### 断言单元：规则管形式，模型管语义（`/v2/verify`）

复合句（“……，虽未宣布 PHEIC，……”）曾被当一句判 supported；条件句曾被当已陈述事实。程序判断不了一句有哪些断言，所以：

- `segment_rules.py` 按逗号、分号、顿号和连接词切候选句段 S1…；句段只是记账单位，模型读整句和相邻句。单字连接词（并 且 而 但）只在独立成词处切，英文连接词只按整词。
- 模型报告单元，每个落在一个句段并给逐字片段；`unit_rules.py` 编号 U1…，在句段内定位片段（找不到或不唯一则作废并写明原因），由程序汇总句子判定。
- `form_check` 只写程序能确定的（每个句段有单元、无空结果、重叠已声明、`governed_by` 能映射、否定词没丢），从不声称拆分完整；`semantic_split` 是模型自评，不是 `complete` 时句子不能判 supported 或 no_claim。矛盾不被压下。
- supported / contradicted 单元要有定位到的短引，或否定事实的结构字段（路径和值对得上）。程序不要求短引含否定词（死亡数 0 支持“无死亡”）。否定、条件、连接词表只是切点和提示（ConText 思路），不是语义证明，随 `RULES_VERSION` 变。词表错只会多一句待核或漏一刀，不会单独造成错误的 supported。
- 批次：每批最多 4 句、24 个句段、同一段；超过 8 个句段或 300 字单独成批；超过 24 个句段不送模型（`batch_limit`）。输出被截断时对半拆批直到单句（`output_truncated`），n 句最多 2n-1 次调用，都计入 `max_llm_calls`。
- 证据要支持断言本身：“原文没提到 X”不能支持“X 没发生/未触发”，只能支持“材料未报告 X”。
- 条件句三种角色：条件（`condition`，无断言）、后果（`governed_by` 指向条件的全部句段）、并列事实（照常核验）。后果连同条件判断：条件是前提，不需要原文支持；单纯情景是 `no_claim`；超出条件所给的是 `insufficient`。程序对以 则/那么 开头的句段给 `consequent_of` 提示，不是判定。
- **按句分组回答**：模型回答 `{"claims":[{"sentence", "units":[...], "split":{...}|null}]}`，句号每组写一次且在最前。扁平形式下模型曾在每个单元漏写句号、重试照抄，整批失败。没有 `sentence` 的组无效；不在本批的组不读；没被任何组提到的句子没有单元，保持待核。不修补、不兜底。
- 每份材料的时间信息（发布、首见、证明可得、回放模式）随引用送给模型；比句子所称文件更晚的日期只作线索（`time_clues`），不是判定。

### 报告节与槽

雷达写稿前列出报告必须回答的问题（J1、J2…），核验时说明每段属于哪一节。

- `/v1/generate` 收 `slots`，返回扁平的 `sections`（`SectionsOut`，提示词 `WRITE_BY_SLOT` = `WRITE` 加结构）。不带 `slots` 的请求用 `WRITE` 和 `DraftOut`，与以前逐字节一致（golden 钉住提示词哈希）。没有 recommendation 段：请求不带目标。BioCheck 不核对槽号是否来自请求，由雷达放置和丢弃。
- `/v2/verify` 收 `sections`：落在 judgment、gaps、scenarios、recommendation 之外的句子属于事实节，推断单元在那里不能判 supported。gaps 段可以解释证据局限及其有依据的含义，所以不降级。节不告诉模型，规则归程序。
- `/v1/revise` 可读 `/v2/verify` 的结果：没有 `quotes` 的句子取各单元的短引；单元里没有 `scope_span` 的对应物，所以 v2 结果只修订矛盾句。
- 未做：`[R#]` 回执作引用；报告结构的确定性规则（节齐全、有目标才有建议）；把节告诉核验模型。

### 抽取一致性 checker 的版本

`/v1` 和 `/v3` 的 extraction-consistency 回答加工产物是否与固定原文对应；Fabric 和雷达把回答和数据存在一起，所以同一请求在同一 checker 版本下永远得同一回答。

- 任何规则、词表、单位表、数字转换的改动都提升所在模块的 `CHECKER_VERSION`；旧版本不改，在发布它的提交里可复现。服务只回答当前版本，要旧版本就跑那个提交。
- 一个契约一个模块：`item_rules.py`（v1）、`dimension_rules.py`（v3）；`measurement_rules.py` 被 v3 以当前规范化（extraction_normalize v4、v5、v6）调用，不复制；契约 v2 没有路由。
- 规范化规则在 `app/normalize.py`（Fabric 的测量产出方复制了其中读数字的几条）。规则改动成批发布，不为每个边界情况发一版。
- `tests/fixtures/checker_golden.jsonl` 冻结当前版本的回答，只在升版本时用 `tests/golden.py` 重新生成。

### 契约 v3 的英文写法（checker v17）

D1 链路第一批 WHO 疫情公告（24 个封存窗口，AI 辅助标注、未经人工复核）的 40 个候选，v16 一个都没判 consistent，连两条手写的正确读法也不行：旧规则是为一句一个数量、句中有期间、写“累计”的中文写的。v17 只加那批正确句子需要的规则，且只对不含中日韩字符的局部句生效（中文回答不变）：

- 一句多个数：数量短语从它的数字到下一个数量；括号里的百分数不是另一个数量，括号里的逗号不切组。
- 列表共用一个期间：期间是句中唯一日期、在所有数量之前或之后、每个数量（第一个除外）由 including / and / of which 引出时，属于每个成员。“bringing the total to 40” 不是成员。
- 总量：`a total of` 是总量词；`As of <date>, a total of N` 是累计写法；只有起点的期间（since September 2012）是累计，不是 flow。标题点名对象（Dengue - Nepal）不限制总量，英文比较时忽略大小写。
- 期间写法：混合精度区间首月从 1 日起；ISO 周和“截至某日的一周”是七天；`On 12 November 2015` 是一天；`Between 2017 and 2021` 是月区间；`since …` 只有 `start`。无年份、`to date`、`So far` 仍拒绝。
- 有结构依据的错读判 mismatch（条目 inconsistent）：数字粘在词后（case1）、写出区间的一端、更正声明里的旧值、`N of the M confirmed cases died` 的 N 当病例数。紧跟指标末词的一位数字（linked 2）可能是脚注，判 unsupported。只是有歧义的保持 unchecked，没有规则去猜。
- 拼写的 one 到 twelve 是数字。
- 未决：后面逗号组里的事件词、动词后的地点、区间上的累计断言、句子不带的期间、只在标题里的对象，都保持 unchecked。
- 调用方须显式写明 `biocheck.extraction_rules.v17`，产出方须写新的规范期间（周和混合精度用日区间、年用月区间、开放区间只写 `start`）。`PeriodValue` 接受只有 `start` 的区间。

## 从公告里读数字（设计思路，未实现）

2026-11-16 起，Fabric 和雷达删掉了“把公告里的数字抽出来存成序列”的测量程序（只服务 WHO DON 一个来源、78 条公告，线上没跑过）。
留下的只有下面这几条想法，以后真要用公告里的数字时照着做；这里没有代码。

- **数字要有出处**：每个数字都引自某个来源的某一个版本里的某一句原文（来源、版本号、原句），没有原句的数字不用。
- **没有公告不等于没有疫情**：通报是选择性的，零条公告只说明“没有通报”，不能当成“零病例”或“已平息”。
- **更正是新的一条，不是覆盖**：后来的公告更正了前面的数字，就记成“新值取代旧值”，旧值和它的出处都留着，能看出改过几次、谁改的。
- **累计数和新增数要标清楚**：同一句话里“累计 120 例”和“新增 12 例”是两种量，必须标明是哪种、截至哪天，不能互相比较或相加。
- **谁来读、谁来核**：数字由分析时的模型从清洗正文里读出并引用原句；BioCheck 用规则核对这个数字确实在引用的原文里、单位和口径对得上。
  不另建抽取流水线，也不预先存成序列。
